## 1. 任务回顾

### 1.1 目标

把「销售订单只读查询」升级为可端到端执行的写流程：

```text
创建订单 → 提交 → 审核 → 反审核 / 删除
        ↘ 高风险动作进入审批（API 双人复核 / CLI 同步确认）
        ↘ 幂等 + Saga 补偿 + 写账本 + 证据链
```

并让 WebUI 能完成：

- 发起写操作
- 看到「待审批」状态与 approval_id
- 审批面板：通过 / 拒绝 / 执行
- 审批通过后查回订单状态

### 1.2 本卡做

| 能力 | 说明 |
|------|------|
| 沙箱写入 | Save / Submit / Audit / UnAudit / Delete 五个端点 |
| 可变数据 | 沙箱从只读种子升级为可增删改的内存订单库 |
| 写工具 | 5 个销售订单写工具，Schema 自动生成 |
| 工具框架 | `ToolDefinition` 支持远程写执行器 `remote_runner` |
| 审批 | API 的 `confirm` / `dual_approve` 均走审批单；CLI 保持同步确认 |
| 幂等/账本 | 复用 `WriteCoordinator`、Saga、Idempotency、WriteLedger |
| 控制台 | 新增「审批」面板：列表 / 通过 / 拒绝 / 执行 |
| 测试 | 沙箱契约、工具、审批闭环、恰好一次、UI 面板 |

### 1.3 本卡明确不做

- **不做采购订单写入**：本卡只覆盖销售订单，采购后续按同一模板扩展
- **不做真实金蝶写入协议的全字段兼容**：沙箱实现官方 `Save/Submit/Audit/UnAudit/Delete` 的最小可信子集
- **不做审批流配置后台**：审批角色/票数继续用 `config/approval_rules.py`
- **不做订单编辑/变更**：只做创建、状态流转、删除
- **不做批量导入/批量审核**
- **不做租户级审批人矩阵**：沿用现有角色模型

### 1.4 验收标准

- [x] 沙箱五端点契约测试通过（成功/非法状态迁移/会话失效）
- [x] 写工具可被 LLM 选中并通过 Guard 1~5、权限、风险
- [x] API 完成「创建 → 提交 → 审核」闭环，审批通过后恰好执行一次
- [x] 拒绝/过期审批零执行；重复审批/重复执行不重复写
- [x] 账本可回放每次写操作，hash 链校验通过
- [x] WebUI 审批面板可完成通过/拒绝/执行并显示状态
- [x] `make check` 全绿；读流程与现有测试不回退

## 3. 关键设计决策（需审批）

### D1. 只做销售订单，状态机固定

| 动作 | 允许的当前状态 | 目标状态 |
|------|----------------|----------|
| Save（创建） | — | `Z`（暂存） |
| Submit | `Z` / `A` | `B`（审核中） |
| Audit | `B` | `C`（已审核） |
| UnAudit | `C` | `A`（创建） |
| Delete | `Z` / `A` | 删除 |

- 非法迁移返回业务错误，不做“尽力而为”
- `D`（重新审核）本卡不主动产生，保留给真实环境
- 说明：`UnAudit → A` 为沙箱契约假设，真实环境联调时再核对

### D2. 沙箱订单库从只读种子改为可变内存库

```python
class SalesOrderStore:
    def orders(self) -> tuple[SalesOrder, ...]: ...
    def create(self, ...) -> SalesOrder: ...
    def submit(self, bill_no: str) -> SalesOrder: ...
    def audit(self, bill_no: str) -> SalesOrder: ...
    def unaudit(self, bill_no: str) -> SalesOrder: ...
    def delete(self, bill_no: str) -> None: ...
    def reset(self) -> None: ...
```

- 启动时用现有 `ORDERS` 种子初始化
- `threading.Lock` 保护写操作（uvicorn 单进程多线程）
- 单号生成：`SO9xxxxx` 递增，跳过种子已有单号
- 金额：`quantity * tax_price`，保留 10 位小数字符串
- 客户/物料存在性校验：客户查 `BD_Customer` 种子，物料查库存种子
- `reset()` 供测试 fixture 复位

### D3. 写端点沿用金蝶 `DynamicFormService` 形状

```text
Save:    /DynamicFormService.Save.common.kdsvc
Submit:  /DynamicFormService.Submit.common.kdsvc
Audit:   /DynamicFormService.Audit.common.kdsvc
UnAudit: /DynamicFormService.UnAudit.common.kdsvc
Delete:  /DynamicFormService.Delete.common.kdsvc
```

请求统一 `{"parameters": [...]}`；响应沿用金蝶信封：

```json
{"Result": {"ResponseStatus": {"IsSuccess": true, "Errors": []}, "Id": 1001, "Number": "SO900001"}}
```

- 失败同样 **HTTP 200 + IsSuccess=false**（与真实金蝶一致）
- 会话失效返回 `MsgCode=5`，由客户端归一为认证错误
- 不实现 `IsAutoSubmitAndAudit` 等高级参数

### D4. `KingdeeClient.execute_action` 不自动重试

- 写操作只做一次会话有效性检查；会话失效 → 抛 `KingdeeAuthError`
- **不重试**：网络超时后重放可能重复创建/重复审核
- 幂等由 `WriteCoordinator` 的幂等键在服务层保证
- 返回类型化 `ActionResult`：

```python
class ActionResult(KingPilotBaseModel):
    success: bool
    form_id: str
    bill_no: str = ""
    doc_id: str = ""
    message: str = ""
    response: dict[str, Any] = {}
```

### D5. `ToolDefinition` 增加 `remote_runner`

```python
RemoteRunner = Callable[[KingdeeClient, KingPilotBaseModel], Awaitable[Any]]

@dataclass(frozen=True)
class ToolDefinition:
    ...
    remote_runner: RemoteRunner | None = None

    async def execute(self, client, arguments, *, row_filter=""):
        params = self.params_model.model_validate(arguments)
        if self.remote_runner is not None:
            return await self.remote_runner(client, params)
        ...
```

- 写工具仍设置 `endpoint=SAL_ORDER`（复用 form_id/数据域/权限/风险）
- `build_filter=None`；对应 Guard 需要跳过非查询工具
- `params_model` 不需要 `limit`

### D6. Guard 适配写工具

| Guard | 变更 |
|-------|------|
| Guard 1 Schema | 不变，校验参数模型 |
| Guard 2 FilterString | **非查询工具直接放行**（没有 FilterString） |
| Guard 3 实体预检 | 创建单声明客户/物料引用；动作单不声明（bill_no 由 Guard 5 必填） |
| Guard 4 分页/无条件查询 | **先判断非查询工具再读 limit**；写工具放行 |
| Guard 5 写参数 | 校验业务必填项；引用字段必须是内码 |
| 权限 | 写工具按 `SAL_Order` 数据域与 write 规则判定 |
| 风险 | 写基础分 + 金额 + 审核/删除动作分 |

### D7. 写工具清单

| 工具名 | 动作 | 参数 | 业务必填 |
|--------|------|------|----------|
| `kingdee_create_sales_order` | save | customer_number / material_number / quantity / tax_price / order_date / note | 前 4 项 |
| `kingdee_submit_sales_order` | submit | bill_no | bill_no |
| `kingdee_audit_sales_order` | audit | bill_no | bill_no |
| `kingdee_unaudit_sales_order` | unaudit | bill_no | bill_no |
| `kingdee_delete_sales_order` | delete | bill_no | bill_no |

- 创建工具 `entity_references`：customer_number、material_number
- 动作工具不声明实体引用，避免把单号当客户/物料做预检
- 工具描述明确「写操作，需审批」，帮助 LLM 与知识问题分流

### D8. API 审批：confirm 与 dual 都建单

当前 API 对 `confirm` 用 `DenyConfirmationIO` 直接拒绝，导致创建/提交无法执行。改为：

```text
hitl.level == confirm       → 审批单，required_approvals=1
hitl.level == dual_approve  → 审批单，required_approvals=2
```

- `ApprovalService.create` 增加 `required_approvals` 参数（默认 2，保持旧行为）
- `ApprovalGatewayImpl.ApprovalRequest` 增加 `required_approvals`
- 审批人必须是不同用户，且不能是发起人
- `confirm` 单第一个非发起人审批通过即可执行；`dual` 需要两票
- CLI 不注入 approval gateway，保持同步确认

### D9. 快照与账本

- 新增 `KingdeeSnapshotProvider`：
  - submit/audit/unaudit/delete：按 `bill_no` 查当前订单，作为 before/after
  - create：before=None；after=None（结果中的单号在 `api_response` 与 `ActionResult`）
- `WriteOperation.business_key`：
  - 动作类：`bill_no`
  - 创建类：`CREATE-{approval_id[:8]}`（执行前单号未知）
- 账本仍记录 trace / action / api_request / api_response / before / after / hash
- 创建类的真实单号可在 `api_response` 与 `ActionResult.bill_no` 中回溯

### D10. WebUI 审批面板

- 顶栏新增「审批」按钮，打开右侧抽屉/面板
- 数据：`GET /v1/approvals?scope=inbox`
- 操作：
  - 通过：`POST /v1/approvals/{id}/approve`
  - 拒绝：`POST /v1/approvals/{id}/reject`
  - 执行：`POST /v1/approvals/{id}/execute`（approved 但未执行时）
- 显示：工具名、摘要、发起人、风险分、状态、票数、execution_status
- 审批人切换：登出后用另一个 Key 登录（至少两个不同用户）
- 本卡不新增「创建 Key / 用户管理」页面

### D11. 测试身份

为完成双人复核，测试至少配置 3 个 Key：

| Key | 用户 | 角色 | 用途 |
|-----|------|------|------|
| A | alice | salesperson | 发起创建/提交/审核 |
| B | bob | manager | 第一审批人 |
| C | carol | manager | 第二审批人 |

- 单票 `confirm`：A 发起，B 通过即可执行
- 双票 `dual`：A 发起，B + C 各一票
- C 不能重复 B 的票；A 不能审批自己的单

## 6. 测试矩阵

### 6.1 沙箱写契约

| 用例 | 断言 |
|------|------|
| Save | 返回单号，状态 Z，金额正确 |
| Submit Z/A | 状态变 B |
| Audit B | 状态变 C |
| UnAudit C | 状态变 A |
| Delete Z/A | 订单消失 |
| 非法迁移 | HTTP 200 + IsSuccess=false，状态不变 |
| 会话失效 | MsgCode=5 |
| 客户/物料不存在 | 业务错误，不建单 |
| 单号唯一 | 并发创建不重复 |

### 6.2 写工具

| 用例 | 断言 |
|------|------|
| Schema | 未知参数/缺必填被拒 |
| Guard 2 | 写工具跳过 FilterString 校验 |
| Guard 4 | 写工具不要求过滤条件 |
| Guard 5 | bill_no 必填；创建必填客户/物料/数量/价格 |
| 权限 | viewer 拒绝；salesperson/admin 允许 |
| 风险 | 创建/提交 confirm；审核/删除 dual_approve |

### 6.3 审批闭环

| 用例 | 断言 |
|------|------|
| 创建确认 | A 发起 → 单票通过 → 恰好创建一次 |
| 提交 | 状态 Z/A → B |
| 审核双票 | B+C 通过 → C；同一人重复票无效 |
| 拒绝 | 零执行 |
| 过期 | 零执行 |
| 重复审批/执行 | 不重复写 |
| 重启恢复 | approved 单可手动执行 |
| 账本 | 每次写有记录，hash 链通过 |

### 6.4 WebUI

| 用例 | 断言 |
|------|------|
| 审批列表 | 显示待办、风险、票数 |
| 通过 | 票数 +1；满足票数后自动执行 |
| 拒绝 | 状态 rejected，零执行 |
| 执行 | approved 未执行单可手动执行 |
| 身份隔离 | 发起人看不到自己的审批按钮；跨用户不可代批 |

## 7. 风险与边界

| 风险 | 处理 |
|------|------|
| 创建单号未知 | 用 `CREATE-{approval_id}` 作 business_key，真实单号在 api_response |
| 沙箱协议与真实金蝶差异 | 只实现最小字段子集；真实联调时按官方报文补 |
| 写操作网络超时重放 | 不自动重试；靠幂等键与服务层去重 |
| confirm 单票误执行 | 仍要求非发起人审批；高风险金额升级 dual |
| 审批 UI 多用户切换麻烦 | 测试用 3 个 Key；后续可加用户切换器 |
| 并发写同一单 | 进程内按 approval_id 锁 + 沙箱 store 锁 |
| 现有读流程回归 | 写工具只新增，不改查询工具行为 |

```bash

```

手工闭环（API）：

1. 用 alice Key 发起 `创建销售订单` → 返回 202 + approval_id
2. 用 bob Key `approve` → confirm 单票后执行，查订单状态 Z
3. 用 alice Key `提交` → 202，bob 通过 → 状态 B
4. 用 alice Key `审核` → 202，bob + carol 各通过 → 状态 C
5. 用 carol Key `反审核`/`删除` 按风险档验证
6. 查询订单确认状态；账本按 trace_id 回放
